# 月度绩效「成果记录 R」对接说明（v2.2）

> 本文档供前端对接「成果记录 R」功能使用。基于 v2.0 / v2.1 增量编写，**仅说明变更点**，未提及的接口/字段保持 v2.0 / v2.1 不变。
> 完整接口请参见 `个人月度绩效接口文档-v2.0.md`，取消状态参见 `月度绩效-取消状态对接说明-v2.1.md`。

## 一、背景与语义

关键成果 K 切换到「已完成」时，用户需填写**成果记录 R**（Result），记录该 K 实际产出了哪些成果。R 是 K 的子记录（1:N），仅 `content` 文本字段，可多条。

**核心规则**：

| 场景 | R 的处理 |
|---|---|
| K 切换到**已完成(2)** | 前端提交 `records`（多条文本）：传了就**全量覆盖**旧 R，不传（null）或传空数组就**清空**旧 R |
| K 从已完成切回**进行中(1)**（返工） | R **保留不动**，下次再切完成时可继续编辑（再次提交会覆盖） |
| K 切到**已取消(3)** | R **保留不动**（取消不抹除已填成果） |
| K 从已取消恢复为未开始(0) | R **保留不动** |
| **删除 K** | R **同步物理删除**（仅删除才清 R） |
| 删除目标 O | 级联删除其下所有 K 的 R |

一句话：**R 只随「切完成」动作提交，只随「删 K」消失**，其余状态流转都保留 R。

## 二、接口变更

### 切换 K 状态（扩展）

`PATCH /api/key-results/{id}/status`

请求体在 v2.1 基础上新增可选字段 `records`：

```json
{
  "status": "2",
  "records": ["完成首页改版，新版上线", "性能提升 40%", "用户满意度 +15%"]
}
```

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| status | string | 是 | `"0"`/`"1"`/`"2"`/`"3"`；须为合法流转（见 v2.0/v2.1 状态机），否则 409 |
| cancelReason | string | 否 | 最长 500 字符；仅 status=`"3"` 时写入（同 v2.1） |
| records | string[] | 否 | **仅 status=`"2"` 时生效**；每条最长 2000 字符，最多 50 条 |

**records 语义（重要）**：

| `status` 目标值 | `records` 传值 | 行为 |
|---|---|---|
| `"2"` 已完成 | `["A","B"]` | **全量覆盖**：删旧 R，写入 A、B |
| `"2"` 已完成 | `[]` 空数组 | **清空**：删旧 R，不写入 |
| `"2"` 已完成 | 不传 / null | **清空**：删旧 R，不写入 |
| `"1"`/`"0"`/`"3"` | 任意值 | **忽略**，R 保留不动 |

> 即：**只有切到「已完成」时 records 才生效**，且「传了覆盖、不传清空」统一为「不传 = 清空」。这样返工后再完成时，前端若不重新填 R，旧 R 会被清空，避免残留过期内容。前端应在切完成表单里回填现有 R 供用户编辑。

**响应**：返回更新后的 K（`KeyResultVO`，新增 `records` 字段，见第三节）。

```json
{
  "code": 200,
  "data": {
    "id": 11,
    "name": "完成首页改版",
    "description": "重构首页布局与交互",
    "status": "2",
    "planCompleteDate": "2026-07-15",
    "completeDate": "2026-07-12",
    "cancelReason": null,
    "sprintIds": [],
    "records": ["完成首页改版，新版上线", "性能提升 40%", "用户满意度 +15%"]
  }
}
```

## 三、数据结构变更

### KeyResultVO 新增字段

| 字段 | 类型 | 说明 |
|---|---|---|
| records | string[] | 成果记录 R 列表；K 未填过 R 时为空数组 `[]`，非 null |

**所有返回 K 的接口都携带 `records`**，包括：
- `GET /api/objectives?month=`（目标列表内嵌的 keyResults）
- `POST /api/key-results`（新建 K）
- `PUT /api/key-results/{id}`（编辑 K）
- `PATCH /api/key-results/{id}/status`（切换状态）

### 完整 KeyResultVO（v2.2 汇总）

```json
{
  "id": 11,
  "name": "完成首页改版",
  "description": "重构首页布局与交互",
  "status": "2",
  "planCompleteDate": "2026-07-15",
  "completeDate": "2026-07-12",
  "cancelReason": null,
  "sprintIds": [101],
  "records": ["完成首页改版，新版上线"]
}
```

## 四、R 不提供独立接口

R 没有独立的增删改查接口，其生命周期完全由 K 的状态变更驱动：

- **填写/修改 R**：只能在 `PATCH /api/key-results/{id}/status` 切到「已完成」时，通过 `records` 字段提交（全量覆盖）。
- **查看 R**：通过 K 所在的接口响应（`KeyResultVO.records`）获取，无单独的「查 R 列表」接口。
- **删除 R**：只有删除 K 时级联删除，无单独的「删 R」接口。

如未来需要独立编辑 R，再单独提需求扩展。

## 五、R 的顺序（重要）

R 是**有序列表**，顺序由**保存时的数组顺序**决定，查询时按相同顺序返回。

- **前端无需传排序字段**：`records` 数组的元素顺序即顺序，后端按数组下标依次落库。
- **查询按落库顺序返回**：后端按 R 的主键自增 id 升序返回（id 严格反映保存顺序），前端拿到的 `records` 顺序与上次提交的一致。
- **全量覆盖时整体重排**：每次切完成提交 `records`，旧 R 全部删除、按新数组顺序重新写入。若用户调整了条目顺序（如拖拽排序后提交），返回顺序随之更新。

**示例**：
```
提交: records: ["成果A", "成果B", "成果C"]
返回: records: ["成果A", "成果B", "成果C"]   // 顺序一致

再次提交（调整顺序 + 改内容）: records: ["成果C改", "成果A", "新成果D"]
返回: records: ["成果C改", "成果A", "新成果D"]  // 按新顺序
```

前端如需支持 R 的拖拽排序，只需调整 `records` 数组顺序后随切完成提交即可，无需额外字段。

## 六、前端联调要点

1. **切完成时弹窗填写 R**：K 从「未开始/进行中」切到「已完成」时，前端应弹窗让用户填写多条成果记录（`records` 数组），每条最长 2000 字符，最多 50 条。
2. **回填现有 R**：返工（已完成->进行中）后再次切完成时，前端应在弹窗里**回填当前已有的 `records`**（从 K 详情取），用户可在此基础上增删改，提交时整体覆盖。**若用户清空所有条目再提交，后端会清空 R**。
3. **R 非必填**：切完成时 `records` 可不传或传空，后端不会拦截（不强制必填）。但建议前端做「至少填一条」的引导，避免空成果。是否强制必填由前端产品决定。
4. **展示 R**：K 卡片为已完成状态时，展示 `records` 列表（如「成果记录：1. xxx 2. xxx」）。进行中/已取消状态若 `records` 非空，也建议展示（说明之前完成过、有成果留痕），但可置灰或折叠。
5. **records 只在切完成生效**：前端切到进行中/取消/恢复时，**不要传 `records`**（传了也会被忽略）。只有 `status:"2"` 时才传。
6. **无新增错误码**：R 功能复用现有 409（状态流转非法）、422（参数校验失败）、404（越权）。`records` 超长/超条数返回 422。
7. **空数组语义**：`records: []` 和不传 `records` 在切完成时都表示清空。前端若想「保留旧 R 不动」，只能在切完成时把旧 R 原样传回（因为切完成必然触发覆盖/清空）。
8. **顺序由数组顺序决定**：`records` 数组的元素顺序即展示顺序，前端无需传排序字段。如需支持拖拽排序，调整数组顺序后提交即可（见第五节）。

## 七、交互流程示例

### 场景 A：首次完成 K，填写 R

```
1. 用户点击 K 的「完成」按钮
2. 前端弹窗，用户输入 3 条成果记录
3. 前端调用 PATCH /api/key-results/{id}/status
   请求体: { "status": "2", "records": ["成果A","成果B","成果C"] }
4. 后端保存 3 条 R，返回 K（records 含 3 条）
5. 前端展示 K 已完成 + 成果记录列表
```

### 场景 B：返工后再次完成，修改 R

```
1. K 当前已完成，有 2 条 R
2. 用户点「取消完成」-> 切回进行中（不传 records）
   请求体: { "status": "1" }
   后端保留 2 条 R 不动，返回 K（records 仍含 2 条）
3. 用户再次点「完成」
4. 前端弹窗，回填现有 2 条 R，用户改成 3 条
5. 前端调用 PATCH /api/key-results/{id}/status
   请求体: { "status": "2", "records": ["新成果A","新成果B","新成果C"] }
6. 后端全量覆盖：删旧 2 条，写新 3 条
```

### 场景 C：取消 K（R 保留）

```
1. K 当前已完成，有 2 条 R
2. 用户点「取消完成」-> 进行中（R 保留）
3. 用户点「取消」-> 已取消，填写取消原因
   请求体: { "status": "3", "cancelReason": "需求变更" }
   （不传 records，后端忽略，R 保留）
4. 后端返回 K（status=3, cancelReason=需求变更, records 仍含 2 条）
5. 前端展示已取消 + 置灰展示 R（说明曾有成果）
```

### 场景 D：删除 K（R 同步删除）

```
1. 用户点「删除」K
2. 前端调用 DELETE /api/key-results/{id}
3. 后端删除 K + 级联删除其下所有 R
4. R 随 K 一起消失，无法恢复
```

## 八、已定决策（v2.2 最终结论）

1. **R 仅 content 文本字段**：每条最长 2000 字符，最多 50 条。无标题、无附件、无时间戳字段。
2. **R 随切完成提交，无独立接口**：R 的填写/修改只能通过 `PATCH /api/key-results/{id}/status`（status=2）的 `records` 字段完成，全量覆盖语义。
3. **不传 = 清空**：切完成时 records 为 null 或空数组都清空旧 R，避免返工后旧 R 残留。前端需回填现有 R 供用户编辑。
4. **R 保留场景**：切回进行中、切到已取消、已取消恢复--R 都保留不动。
5. **R 删除场景**：仅删除 K 时级联物理删除 R；删除 O 时级联删除其下所有 K 的 R。
6. **R 不参与派生计算**：R 是成果留痕，不影响 O 的 progress/status 计算（派生仍按 K 的 status 算，见 v2.0/v2.1）。
7. **R 有序，顺序由数组顺序决定**：前端不传排序字段，`records` 数组顺序即保存顺序，查询按此顺序返回（后端按自增 id 升序）。
