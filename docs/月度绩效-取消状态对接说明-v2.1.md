# 月度绩效「取消」状态对接说明（v2.1）

> 本文档供前端对接「取消」状态使用。基于 v2.0 接口文档增量编写，**仅说明变更点**，未提及的接口/字段保持 v2.0 不变。
> 完整接口请参见 `个人月度绩效接口文档-v2.0.md`。

## 一、背景与语义

月度绩效在月初定好目标 O 与关键成果 K，但实际执行中可能出现**某项需求未确定下来、无法落实**的情况，导致该 K 无法推进。此时需要将其标记为「取消」，而非删除。

**取消 vs 删除（重要区分）**：

| 操作 | 语义 | 数据处理 | 适用场景 |
|---|---|---|---|
| **取消** | 业务无法落实，任务终止 | 保留记录，状态置为已取消，**不参与进度统计** | 需求未定/方案变更/外部依赖取消，需留存复盘 |
| **删除** | 配置错误，不应存在 | 物理删除，**记录消失** | 误建、重复配置、测试数据清理 |

一句话：**取消是业务终态（留痕），删除是数据清理（抹除）**。

## 二、状态码变更

### 关键成果 K 状态码（新增 `3`）

| 数字码 | 含义 | 建议文案 | v2.0 已有 |
|---|---|---|---|
| `"0"` | 未开始 | 未开始 | ✅ |
| `"1"` | 进行中 | 进行中 | ✅ |
| `"2"` | 已完成 | 已完成 | ✅ |
| `"3"` | **已取消** | **已取消** | 🆕 新增 |

### K 状态机（扩展）

在 v2.0 基础上新增取消相关流转：

```
未开始(0) ──取消──> 已取消(3)
进行中(1) ──取消──> 已取消(3)
已取消(3) ──恢复──> 未开始(0)
```

**规则**：
- `未开始`、`进行中` 可取消（→ `3`）。
- `已取消` 可恢复为 `未开始`（→ `0`），相当于重新纳入推进。
- `已完成(2)` **不可直接取消**：已完成代表成果已落地，如需取消须先「取消完成」回到进行中(1)，再取消。保护已完成数据。
- 其余流转规则同 v2.0（详见 v2.0 文档状态机）。

非法流转示例（返回 409）：已完成→已取消、已取消→进行中、已取消→已完成、同状态切换。

## 三、对派生计算的影响（核心，前端必读）

**已取消的 K 不参与 O 的派生计算**，即从 progress 分母、status 派生中排除。否则取消的 K 会拉低完成率，失真。

### O 的派生状态（扩展）

O 的 `status` 派生规则调整为（先过滤掉已取消的 K，再看剩余有效 K）：

| 条件（effectiveK = 该 O 下非取消的 K） | O 派生 status |
|---|---|
| effectiveK 为空（即无 K，或所有 K 都已取消） | `"3"` 已取消 |
| effectiveK 全部未开始(0) | `"0"` 未开始 |
| effectiveK 任一进行中(1) 或部分已完成(2) | `"1"` 进行中 |
| effectiveK 全部已完成(2) | `"2"` 已完成 |

### O 的 progress 计算（调整）

```
progress = 已完成K数(2) / 有效K总数(非取消) × 100
```

- 分子：状态为已完成(2) 的 K 数（取消的不算）。
- 分母：**排除已取消(3)** 的 K 数。
- 若有效 K 总数为 0（全取消或无 K）→ `progress = 0`。

**举例**：O 下 4 个 K——2 已完成、1 进行中、1 已取消。
- v2.0（错误）：progress = 2/4 = 50%
- v2.1（正确）：有效 K = 3（2 完成 + 1 进行中），progress = 2/3 = 66%

### O 的完成时间派生（调整）

- `planCompleteDate`：取**有效 K（非取消）**中 `max(planCompleteDate)`；全取消时为 null。
- `actualCompleteDate`：仅当**所有有效 K** 都已完成(2) 时 = `max(completeDate)`；否则 null。

## 四、接口变更

### 1. 切换 K 状态（接口7，扩展）

`PATCH /api/key-results/{id}/status`

请求体 `status` 新增合法值 `"3"`，并新增可选字段 `cancelReason`：
```json
{
  "status": "3",
  "cancelReason": "需求未最终确定，暂无法推进"
}
```

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| status | string | 是 | `"0"`/`"1"`/`"2"`/`"3"`；须为合法流转（见状态机），否则 409 |
| cancelReason | string | 否 | 取消原因，最长 500 字符；仅 status=`"3"` 时写入，其他切换忽略 |

**completeDate / cancelReason 维护**：
- → 已取消(3)：**清空 completeDate**（取消即未真正完成）；写入 `cancelReason`（若传入）。
- 已取消(3) → 未开始(0)（恢复）：**清空 cancelReason**；completeDate 保持 null。
- → 已完成(2)：completeDate 设为当天（已有值不覆盖）。
- → 进行中(1)：completeDate 清空。

**响应**：同 v2.0，返回更新后的 K（含 `cancelReason` 字段）。

### 2. 新增 K（接口5，无结构变更）

`status` 字段**不允许传 `"3"`（已取消）**——取消是执行过程中发现无法落实才做的操作，新建即取消无意义，后端返回 422。前端新建表单不提供「已取消」选项。

`status` 可传值：`"0"` 未开始（默认）/ `"1"` 进行中 / `"2"` 已完成。

> 注意：`cancelReason` 不在创建请求中提供，仅在状态切换到已取消时（接口7）传入。

### 3. 编辑 K（接口6，规则扩展）

已取消的 K 编辑规则与已完成一致——**只允许编辑名称和描述**，`planCompleteDate` 不可改（返回 409）。如需调整计划时间，先恢复为未开始。

### 4. 删除 K（接口8，规则扩展）

- 已取消的 K **允许删除**（取消已是终态，删除即清理记录）。
- 已完成的 K 仍禁止删除（同 v2.0）。

### 5. 删除目标 O（接口4，规则扩展）

- 目标 O 下存在**已完成**的关键成果时仍禁止删除（同 v2.0）。
- 目标 O 下**仅存在已取消**的 K 时，**允许删除**（取消的 K 不阻止 O 删除）。
- 删除 O 仍连带删除其下所有 K（含已取消）。

## 五、对月度总览的影响

月度总览接口（`GET /api/plan/overview?month=2026-07`）的绩效统计同步调整：

| 字段 | v2.0 | v2.1 |
|---|---|---|
| `perfTotal` | 该月所有 K 数 | 该月**有效 K 数**（排除已取消） |
| `perfDone` | done 的 K 数 | done 的 K 数（不变） |
| `perfRate` | perfDone/perfTotal | perfDone/**有效K数** |

**效果**：取消的 K 不再拉低月度完成率。

## 七、错误码（增量）

| code | 含义 | 新增触发场景 |
|---|---|---|
| 409 | 状态流转非法 | 已完成→已取消、已取消→进行中/已完成、已取消 K 改计划完成时间 |
| 409 | 资源冲突 | 目标下存在已完成 K 时删 O（同 v2.0，不变） |

## 八、前端联调要点

1. **状态映射表新增 `"3"` → 「已取消」**，建议用灰色/删除线样式区分，与未开始/进行中/已完成视觉区分。
2. **取消入口**：仅在 K 状态为「未开始」「进行中」时显示「取消」按钮；「已完成」不显示（需先取消完成回退）。
3. **取消时弹窗输入原因**：点击「取消」应弹窗让用户填写取消原因（`cancelReason`，最长 500 字符），随 `KeyResultStatusReq` 传入。原因非必填，但建议前端做必填校验以留存复盘信息。
4. **恢复入口**：仅在 K 状态为「已取消」时显示「恢复」按钮，恢复后变回「未开始」。恢复无需传 cancelReason（后端自动清空）。
5. **展示取消原因**：K 卡片为已取消状态时，展示 `cancelReason` 内容（如「取消原因：需求未确定」）。
6. **进度展示**：O 的 `progress` 已排除取消的 K，前端直接用即可，无需自行过滤。
7. **取消的 K 仍展示在列表中**（keyResults 数组里），但建议置灰/折叠，与正常 K 区分。
8. **O 卡片展示取消数**：O 的 `cancelledCount` 字段表示该 O 下已取消的 K 数，前端在 O 卡片上展示「N 项已取消」（如 `cancelledCount > 0` 时显示）。
9. **编辑限制**：已取消的 K，前端编辑表单应禁用「计划完成时间」字段（后端也会拦截返回 409）。
10. **删除限制**：已完成的 K 禁用删除按钮；已取消的 K 允许删除。
11. **O 整体取消**：当 O 下所有 K 都已取消，O 的 `status` 返回 `"3"`，前端可整体置灰展示。

## 九、已定决策（v2.1 最终结论）

1. **O 卡片显示「N 项已取消」**：`ObjectiveVO` 新增 `cancelledCount` 字段（int，派生），值为该 O 下状态为已取消(3) 的 K 数量。前端在 O 卡片上展示「N 项已取消」。
2. **记录取消原因**：`KeyResultVO` 新增 `cancelReason` 字段（string，最长 500 字符）。切换到已取消(3) 时，前端在 `KeyResultStatusReq.cancelReason` 传入原因；后端存入并返回。恢复（取消→未开始）时后端自动清空 `cancelReason`。
3. **恢复后状态**：已取消(3) 恢复后统一回到未开始(0)，不恢复到取消前的状态。
